# 要件定義書 — 一人暮らし新生活 総合最適化ナビ

吉川徹財団 第4期奨学生 応募ポートフォリオ用プロジェクト（締切: 2026-10-18）

## 1. 背景

一人暮らし大学生は「収入（バイト・扶養の壁）」と「支出（固定費・経済圏）」を
別々に、かつ勘と経験だけで管理しがちで、最適化の機会を逃しやすい。
開発者自身が2026年3月の一人暮らし開始後に実際に直面した2つの課題

- 複数バイト（CAZAN珈琲店＋VEXUM）の掛け持ちシフトと扶養の壁のバランス管理
- 銀行・カード・証券・通信キャリアの「経済圏」の非効率（ゆうちょ経由NISAの高信託報酬など）

を出発点に、開発者自身の実体験に基づいたロジックで解決するツールとして設計する。

## 2. イシュー定義（本質的な問い）

**最上位イシュー**: 「一人暮らし大学生は、なぜ収入・支出の両面で最適化の機会を逃すのか？」

良いイシューの3条件で検証:
- 本質的な選択肢を含むか → Yes（対策を打つかどうかで可処分所得・手取りが変わる）
- 深い仮説があるか → Yes（「知識や意欲がないから」ではなく、「知っていても横断的に可視化する手段がないから」という、通説とは違う仮説を置く）
- 答えを出せるか → Yes（開発者自身の実データと公的統計で検証可能）

**仮説（スタンス）**: 一人暮らし大学生が最適化に失敗するのは、意欲や知識の欠如ではなく、
収入（バイト×扶養の壁）と支出（経済圏）を横断して「今の自分の状態」を一望できるツールが
存在しないからではないか。

## 3. Whyツリー：なぜ最適化の機会を逃すのか（MECE分解）

```
問題：一人暮らし大学生が生活最適化の機会を逃す
├─ 収入面の見落とし
│   ├─ 複数バイトを横断した年収管理をしていない（単一バイト前提のツールしかない）
│   └─ 扶養の壁の制度改正（103万→123万等）を把握し損ねる
├─ 支出面の見落とし
│   ├─ 銀行・カード・通信・NISAがバラバラに契約され、比較検討する接点がない
│   └─ サブスク・準固定費（交際費等）が「単発の出費」と誤認され、家計への影響を過小評価される
└─ 統合的な可視化の欠如
    └─ 収入と支出を1つの画面で意思決定材料として見れる場所がない
```

重複チェック: 3分類はそれぞれ独立した原因（収入/支出/統合の可視化）で重なりがない。
漏れチェック: 「生活最適化」を妨げる主要因はこの3分類でカバーできていると判断（他には？を自問し、
「時間的余裕の欠如」等も検討したが、これは本プロダクトのスコープ外＝別イシューとして切り分けた）。

## 4. Howツリー：施策への変換（機能要件のMECEな導出）

```
目標：一人暮らし大学生の"見落とし"を解消する
├─ 収入面の見落としを解消する    → モジュール1: マルチジョブ扶養最適化シミュレーター
├─ 支出面の見落としを解消する    → モジュール2: 経済圏・固定費最適化診断
└─ 統合的な可視化を提供する      → モジュール3: 統合サマリーダッシュボード
```

Whyツリーの3分類とHowツリーの3施策が1:1で対応しており、機能がMECEに導出されている
（無駄な機能も、埋めるべき漏れもない）ことを確認できる。

## 5. ターゲットユーザーのMECE分解

分解軸は「バイト形態」×「扶養区分」×「経済圏習熟度」。
軸を選ぶ理由: MECEの軸は「分類の正しさ」ではなく「目的」で選ぶべきであり、本プロダクトの
目的が「収入×支出の横断最適化」である以上、この3軸がそのまま価値提供ポイントに直結する。

| 軸 | 選択肢 | 本アプリのフォーカス |
|---|---|---|
| バイト形態 | 単一バイト／複数バイト掛け持ち | **複数バイト掛け持ち**（既存ツールが手薄な領域、[6章]参照） |
| 扶養区分 | 特定扶養親族(19〜23歳)／一般扶養／扶養外 | **特定扶養親族**（2025年改正の恩恵と複雑さが最も大きい層） |
| 経済圏習熟度 | 未整理／整理済みだが非効率／最適化済み | **未整理〜非効率**（最適化済み層には価値が薄いため対象外） |

**主軸ターゲット**: 複数バイト掛け持ち × 特定扶養親族 × 経済圏未整理、の一人暮らし大学生
（＝開発者自身が該当する具体的なペルソナ。実データをデモ値に使う正当性もここから来る）

## 6. 主軸となる目的（So What / Why So）

**主張（Claim）**: 本プロダクトの主軸目的は「開発者自身が、複数バイト×扶養の壁×経済圏の
非効率という自分の課題を解決するために使う、実用ツールを作ること」である。
「気づきを与える社会的プロダクト」という体裁は目的を大きく見せすぎで、一歩引いた
一人称の目的に絞る（下記「仮説への反証」参照）。

**仮説への反証（先に検討）**: 「見える化すれば最適化できる」という仮説には反例がある。
tedori-calc.pages.dev のような機能が充実したツールは既に存在するが、それでも使われていない
学生は多い。開発者自身も、支出が実際に苦しくなって初めて経済圏を調べ始めた経緯があり、
「ツールがなかったから気づけなかった」のではなく「調べ始める"きっかけ"がなかっただけ」
という説明の方が実感に近い。この反証を踏まえ、本プロダクトを「気づきを与える社会的
ソリューション」として大きく打ち出すのはやめ、等身大の一人称ツールとして設計する。

**根拠（Grounds）**:
- 開発者自身、2026年9月の交際費が支出の31.6%を占め単月赤字92,594円になるまで、
  準固定費化（単発ではなく毎月発生するスパイク）に気づかなかった
- ゆうちょ銀行経由のNISAの信託報酬が楽天証券の同種ファンドの2〜5倍であることに
  半年以上気づかなかった
- 2025年の扶養の壁改正（103万→123万円）のような制度変化も、能動的に調べない限り気づけない

**論拠（Warrant）**: これらは「調べるきっかけがあれば気づけたはずのこと」であり、
自分が実際に使うツールとして作ることには意味がある。ただし「他の学生にも同じ効果がある」
とまでは主張しない（反証を踏まえた射程の絞り込み）。

**表現方針（README・小論文・UIコピー）**: 「〇〇を診断できる社会的ツール」という
アピール的な打ち出し方はしない。あくまで「自分の生活を最適化するために作った」という
一人称の開発ストーリーで一貫させる。審査で評価されること（技術力・デザイン力の証明）は
結果的について回るものと位置づけ、それを狙って作った感を前面に出さない。
汎用化・他ユーザーへの展開は「14. 今後の展望」で将来スコープとして扱い、v1のゴールには含めない。

## 7. 競合・類似サービス調査と差別化

| サービス | 強み | 弱み・本プロジェクトとの違い |
|---|---|---|
| [パート・アルバイト手取り計算ツール](https://tedori-calc.pages.dev/) | 106/130/178/201万の壁判定、年間シフトシミュレーターが充実 | 単一バイト前提。経済圏診断なし |
| [扶養範囲内計算シミュレーター](https://ikigai.town/ja/yougo/fuyou-keisan.html) | 表形式で年収帯別の壁を即判定 | 配偶者控除中心（既婚者向け）、学生の複数バイトは想定外 |
| [扶養の壁カウンター(アプリ)](https://play.google.com/store/apps/details?id=com.ototo.watasiha.fuyonokabecounter) | 壁を自由設定できるカウンター | 単発の年収管理のみ、シミュレーションや診断機能はない |
| マネーフォワードME（開発者本人が実際に利用中） | 口座連携による自動記録、資産・サブスク可視化、家計診断機能 | **過去の実績を記録・可視化するツール**であり、「この先どうすべきか」を計算する意思決定シミュレーターではない。複数バイトを横断した壁までの残り稼働時間の逆算や、経済圏を乗り換えた場合の年間差額診断は無い |
| [クレカ診断アプリ](https://credit-card-simulator-two.vercel.app/) | カード×決済ルート診断、カジュアルなUI | カード最適化のみ。収入側（バイト・扶養）とは無関係 |

**差別化ポイント**（4章のHowツリーと対応）
1. **複数バイト横断の最適化**: 既存ツールはほぼ単一バイト前提。実際の時給差
   （1160→1190円 / 1300円）を持つ2つのバイトを横断してシフト配分を最適化する視点は競合にない
2. **収入最適化×支出最適化の統合**: 「壁」計算と「経済圏診断」を1つのダッシュボードで
   扱うツールは見当たらなかった
3. **実体験に基づくロジック**: 楽天経済圏棚卸し（信託報酬比較、ポイント通帳の実務的な
   落とし穴など）を一般化したロジックとして実装し、実体験の裏付けがある
4. **記録ではなくシミュレーション**: マネーフォワードMEのような家計簿アプリは
   「過去の実績を記録・可視化する」ツール。本プロジェクトは口座連携をせず、
   「この先どうすべきか」を計算する意思決定シミュレーターとして役割を分ける
   （開発者自身、両方を併用する前提で設計する）

**開発者自身が使っている既存アプリとの棲み分け（2026-09-26時点で確認済み）**

開発者は現在シフトボード（シフト・給料・税/社保ライン管理）、マネーフォワードME
（口座連携の自動記帳・資産管理）、水色の家計簿アプリ（手入力の家計簿）の3本を使っている。
本プロジェクトで統合するのは「決める」作業のみ:

| 作業 | 今回のツールに統合するか |
|---|---|
| シフト調整・複数バイト横断の壁チェック（≒シフトボードの役割） | **する**。モジュール1がシフトボードを代替する |
| 経済圏の乗り換え判断 | **する**。モジュール2が新規に担う |
| 日々のレシート記帳・口座連携の自動記帳（≒水色アプリ・マネーフォワードMEの役割） | **しない**。記録は既存アプリに任せたまま、役割を分ける |

## 8. 機能要件

### 8.1 モジュール1: マルチジョブ扶養最適化シミュレーター

**入力**
- バイト情報（複数登録可）: バイト名、時給、週の勤務日数、1日の勤務時間
- 家族情報: 特定扶養控除の対象か（19〜23歳）、社会保険上の扶養に入っているか
- 開始月・シミュレーション対象年度

**処理ロジック**
- 各バイトの月間給与を合算し、年間見込み収入を算出（給料とおこづかいを分離する考え方 =
  本人の家計簿分析で得た知見を反映し、「入力するのは給料のみ」と明示）
- 123万円の壁（所得税・住民税、2025年改正後）・社会保険の壁（19〜23歳は2025年10月改正後150万円、それ以外は130万円）に対する
  残り稼働可能額を月別に逆算
- 壁到達が見込まれる月をタイムラインで警告表示

**出力**
- 年間収入見込みのプログレスバー（2本の壁それぞれに対して）
- 「あと月◯時間まで働けます」という残り稼働可能時間の表示
- 壁を超えそうな場合、どのバイトのシフトを何時間減らせば回避できるかの提案

### 8.2 モジュール2: 経済圏・固定費最適化診断

**入力**
- 現在契約中の銀行、クレジットカード/デビットカード、通信キャリア、NISA運用先（選択式）
- 月々の固定費（サブスク等）の一覧（任意入力、複数追加可）

**処理ロジック**
- 各カテゴリごとに「ポイント還元率」「信託報酬」「セット割引」等の代表的な差分を
  ルールベースで比較
- 現状の組み合わせと、最適化した場合の年間の差額（円）を試算

**出力**
- カテゴリ別診断結果カード（現状 vs 推奨、年間差額）
- 総合の年間節約ポテンシャル額

### 8.3 モジュール3: 統合サマリーダッシュボード

- モジュール1・2の結果を1画面に集約
- 月次の手取り収支見込み（収入シミュレーション − 固定費診断後の支出）をグラフ表示
- 3枚のKPIカード: 「壁までの余裕」「経済圏最適化ポテンシャル」「月間手取り見込み」

## 9. データ方針

- **本人の家計簿・バイト時給などの個人データ**: 本人確認済みのため、初期値（デモ用プリセット）
  として実数値を使用可
- **家族の年収など第三者に関わる情報**: 実数値は使わず、**総務省家計調査（単身世帯・34歳以下の
  平均支出 月17.3万円、2025年）**や**JASSO学生生活調査**など公的統計の平均値をデフォルト値として
  採用し、出典を明記する。ユーザーは自分の値に自由に上書きできる
- すべての入力はブラウザのstate内で完結させ、サーバーに送信・保存しない（プライバシー配慮を
  明示し、README/UI上でも「入力データはサーバーに送信されません」と明記）

## 15. 今後の展望（v1のスコープ外）

v1は開発者自身が使う一人称ツールとして完成させることを優先し、以下は将来スコープとして
明示的にスコープ外にする（README「今後の改善点」にも同じ内容を記載する）。

- 汎用化: 他の学生でも使えるよう、扶養区分・バイト形態のバリエーションを増やす
- 「調べ始めるきっかけ」の設計: 家計が実際に苦しくなってから使うのではなく、
  能動的に調べていない段階でも気づける導線（通知・診断の定期実行など）
- 経済圏診断ロジックの精緻化: 現状はルールベースの概算。実際のポイント計算式や
  信託報酬の最新値をAPI等で自動取得する
- 既存の記録アプリとの連携: マネーフォワードME・水色家計簿アプリのCSVエクスポートを
  読み込ませて、経済圏診断の入力を手入力ではなく自動化する
